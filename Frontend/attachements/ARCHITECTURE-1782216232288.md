# IFMS — Technical Architecture & Implementation Plan

| Field | Value |
|---|---|
| **Product** | Integrated Farm Management System (IFMS) |
| **Document type** | Technical Architecture & Implementation Plan |
| **Version** | 2.0 (supersedes the Supabase-only v1 draft) |
| **Status** | For development — pilot |
| **Source of truth** | SRS v1.0 · DESIGN.md v1.0 |
| **Audience** | Developers, technical co-founder, owner (Harrison) |

> **What changed from the v1 draft and why.** The v1 draft treated Supabase as "the backend" and contained a **critical secret-leak bug** plus an **unenforceable field-level-permission design**. This version (a) keeps Supabase only as **free managed Postgres + Storage**, (b) makes a **Django backend** the single API the clients talk to (which is the only place per-worker field permissions can be enforced securely), (c) introduces **Celery + Redis** for background work and **FastAPI** as an isolated AI service for later Claude features, and (d) is honest about what "free" actually buys. Corrections are summarised in §2.

---

## 1. Architectural Principles (ranked)
1. **Security & privacy first** — tenant isolation and field-level permissions enforced **server-side, in code we control**; secrets never reach a client; least privilege everywhere.
2. **Start free, stay cheap, scale cleanly** — demo runs at ~$0; no rewrite to scale, only bigger instances and added services.
3. **Offline-first** — the worker app never blocks on the network (`FR-M17-*`).
4. **Something that works > something clever** — one primary backend (Django), Redis as the single broker/cache to begin, RabbitMQ and FastAPI added only when a concrete need appears.

## 3. The Stack Decision (reconciling Supabase + the Python stack)

You asked for Supabase (free demo), and also Django/FastAPI, Celery, RabbitMQ, Redis. Those are not all "the backend" — here is the coherent split:

| Layer | Choice | Role | Why |
|---|---|---|---|
| **Primary API / business logic** | **Django + Django REST Framework** | The one backend all clients call; owns auth, ORM, migrations, admin, costing, permissions, throttling | Batteries-included = "works" fastest; the admin + ORM save weeks |
| **Database** | **PostgreSQL** (Supabase-managed for demo) | System of record | Free 500 MB tier; standard Postgres — portable, no lock-in |
| **File storage** | **Supabase Storage** (demo) → S3-compatible later | Photos via **signed URLs** | Free 1 GB; swap to any S3 store later |
| **Cache / broker / rate-limit store / Celery result backend** | **Redis** | One service, four jobs | Fewer moving parts than adding RabbitMQ on day one |
| **Background jobs** | **Celery** (worker + beat) | Reports, alert evaluation, SMS/push, sync reconciliation, scheduled reminders | Async/heavy/scheduled work off the request path |
| **Message broker (advanced)** | **RabbitMQ** — *deferred* | Reliable fan-out / complex routing | Add **only** when Redis-as-broker is outgrown; not in MVP |
| **AI service** | **FastAPI** — *Phase 2+* | **Internal-only** microservice (Docker network, never internet-facing; Django calls it with a rotating service token) for **Claude** features (advisory chat, anomaly explanations, report narration) | Async streaming fits LLM calls; keeps AI failures away from core CRUD. Model via `ANTHROPIC_MODEL_ID` env var — default `claude-sonnet-4-6` (cost), `claude-opus-4-8` for hardest reasoning. Use **current** model ids, not deprecated `claude-3-*` |
| **Clients** | **React + TypeScript PWA** (worker + owner) | Offline-first worker app; owner web/dashboard | Single codebase web+installable Android; mature offline (Dexie/Workbox) |

**Anti-patterns explicitly avoided:** splitting CRUD across Django *and* FastAPI; running RabbitMQ *and* Redis-as-broker simultaneously at MVP; letting any frontend hold a privileged key or talk to Postgres directly.

## 5. Data Model (unchanged from SRS §4 — Postgres tables)
Core tables (all carry `tenant_id`): `tenants, users, employees, worker_profiles, production_units, batches, batch_movements, inventory_items, inventory_lots, feed_formulas, feeding_records, health_records, sampling_records, mortality_records, production_records, sales, purchases, payments, tasks, task_executions, alert_rules, alerts, audit_log, conflict_log, cost_allocations`. See SRS §4.2 for fields; migrations are the source of truth (`backend/migrations/`).

> **RLS posture (important nuance):** because Django connects with one DB role, Supabase's `auth.jwt()`-based RLS does **not** auto-apply through Django. Therefore **primary** isolation is **app-layer** (every queryset filtered by `tenant_id` via a base manager + middleware). RLS is kept enabled as **defense-in-depth** (set `app.tenant_id` per request with `SET LOCAL` on a transaction-scoped connection) — but the app layer is the guarantee, not RLS alone.

### 5.1 Connection management (must configure — free Postgres has a small connection budget)
Django opens DB connections per worker/thread, and **Celery workers + beat hold connections too**. Left default, an always-on stack can exhaust the free tier and lock up with `too many clients`. Rules:
- **This stack is long-running on a VM** (not serverless) → use either **(a) direct connection** with `CONN_MAX_AGE` set (persistent connections) and a **modest, counted** number of Gunicorn workers + Celery concurrency that sum **under** the connection ceiling, **or (b) the Supabase Supavisor pooler in *session* mode**.
- **Only if/when a serverless path is added** use the **transaction-mode pooler (port 6543)** — and then you **must** set `CONN_MAX_AGE=0` **and disable server-side prepared statements** (psycopg3), or you get `prepared statement already exists` errors. (`SET LOCAL app.tenant_id` still works in transaction mode because it is transaction-scoped, so the RLS-DiD posture above holds; session-level `SET` does **not**.)
- **Budget connections explicitly:** `gunicorn_workers + (celery_concurrency × celery_workers) + beat ≤ ceiling`. Keep any client-side pool small; do not stack a client pool on top of a transaction-mode server pool.

## 6. Authentication, Authorization & Secrets (security-first)

### 6.1 Identities
- **Owner / Manager / Auditor:** email or phone + password (Argon2id). Optional TOTP 2FA (Phase 2, `[SCOPE+]`).
- **Worker:** **phone + 4–6 digit PIN** — a **custom Django auth backend** (C3). PIN stored Argon2id-hashed. No SMS-OTP on the daily path (workers are offline at dawn).

### 6.2 Tokens & offline unlock
- Short-lived **access JWT (~15 min)** + rotating **refresh token (httpOnly, revocable)**. Claims: `sub, tenant_id, role, worker_profile_id`.
- **Offline unlock:** on first online login the worker app caches an Argon2id hash of the PIN locally (in IndexedDB, never the PIN). Subsequent dawns: PIN is verified **locally** to unlock the app and the queued work; a fresh JWT is obtained on next sync. Device lock + auto-logout + remote session revoke (`FR-M19-3`).

### 6.3 Field-level permissions (the part v1 got wrong)
Enforced in **DRF serializers**, server-side:
```
get_fields(): load worker_profile.field_permissions for request.user
  → for each field: if not visible → DROP from output (never serialized)
                    if not editable → mark read_only
```
Because dropped fields are **never serialized**, hidden money values **do not exist in the response payload** — not hidden in the client. Verified by a test that asserts forbidden keys are absent from JSON for a worker token (`FR-M16-1/2`, `NFR-SEC-2`).

### 6.4 Secrets
- All secrets (DB URL, storage key, **service keys**, SMS/M-Pesa creds, `ANTHROPIC_API_KEY`) live in **backend env only** (Docker secrets / `.env` not committed). 
- Frontends ship **zero** privileged keys (C1). They get a public API base URL and their own JWT, nothing more.
- Photo access via **time-limited signed URLs** minted by Django; the storage bucket is private.

## 8. Rate Limiting (corrects C2)
Defense in depth — **not** reliant on Supabase:
| Tier | Mechanism | Policy |
|---|---|---|
| Edge | **Nginx** `limit_req` | Coarse per-IP ceiling; blunt DDoS/abuse shield |
| App | **DRF throttling** (Redis backend) per scope | reads 100/min·user · writes 30/min·user · photo upload 10/min·user · report-gen 5/min·user |
| Auth | DRF + Redis counter | **login 5/min·IP + lockout/backoff** (brute-force) |
| Background | Celery rate limits + idempotency keys | prevent retry storms / duplicate sends |
Throttle state in Redis; `429` returns `Retry-After`; client does exponential backoff and respects it during sync.

> **Proxy IP correctness (required):** Nginx must set `X-Real-IP` and `X-Forwarded-For`, and Django must set `USE_X_FORWARDED_HOST` + a trusted-proxy/`NUM_PROXIES` config, or DRF per-IP throttling and audit logs will record the **internal proxy IP** for every user instead of the real client. Get this right before relying on IP-based limits.

## 9. Offline Sync (corrects C5)
- **Client write path:** save to IndexedDB (Dexie) with a **client-generated UUID** + `captured_at` (device time) + `status=pending`; photo blob queued; instant "✓ saved" (`FR-M17-1`).
- **Idempotency:** the client UUID is the primary key server-side, so retries never duplicate (`FR-M17-5`). A unique-violation on resend means "already accepted" → mark synced (this is **not** an edit conflict).
- **Sync:** batched upload of pending ops → download config/tasks/alerts (server-authoritative for config) → photo upload (compressed ~300 KB; **GPS captured separately, not from EXIF**, per DESIGN `DS-6`).
- **Conflict (true edit conflict on same record):** last-write-wins by `captured_at`, **loser preserved in `conflict_log`** for owner review — never silently dropped (`FR-M17-3`).
- **Background sync** via Service Worker where supported; otherwise on app-open / reconnect / pull-to-refresh.

## 11. Hosting — what "free" actually means (honest)
Pure serverless free tiers **sleep**, which kills an always-on Celery worker + Redis. The pragmatic free, **always-on** setup:

| Option | What runs there | Cost | Honest caveat |
|---|---|---|---|
| **Oracle Cloud Always-Free ARM VM** *(recommended)* | Django, Celery worker+beat, Redis, Nginx — all via **Docker Compose** | $0, always-on (≈4 ARM cores/24 GB) | One box = single point of failure; you manage the VM. Perfect for demo→early pilot |
| **Supabase Free** | Postgres + Storage | $0 | 500 MB DB / 1 GB storage; **pauses after 7 days idle** (keep-alive job) |
| Upstash Redis (alt) | Redis | $0 tier | daily command cap — fine for demo, watch limits |
| CloudAMQP "Little Lemur" (later) | RabbitMQ | $0 tier | only when RabbitMQ is actually adopted |
| Render/Fly (alt to Oracle) | web only | free web sleeps | background workers **not** free → not ideal for Celery |

> **Verify current free-tier numbers before relying on them** — providers change these. The architecture does not depend on any specific limit; only the bill does.

**Demo deployment = one Oracle VM running `docker compose up` (Django+Celery+Redis+Nginx) pointed at Supabase Postgres/Storage.** That is genuinely free, always-on, and is your real stack — no throwaway work.

## 15. Risk Register
| Risk | Impact | Mitigation |
|---|---|---|
| Single VM = SPOF (demo) | High | Acceptable for demo; nightly DB backup; document one-command redeploy; multi-node when funded |
| Supabase free pause / 500 MB cap | Med | Keep-alive job; rollups/archival (`NFR-DATA`); Pro or self-host Postgres when needed |
| Free Redis/RabbitMQ caps | Med | Monitor; self-host Redis on the VM (it already runs there) |
| Offline auth abuse on lost device | High | PIN hashed locally; device lock; remote revoke; short JWT |
| Field-perm regression leaks money data | High | Automated test asserts forbidden keys absent in worker payloads (CI gate) |
| Celery retry storms | Med | Idempotency keys + task rate limits + backoff |
| Service-key leak (the v1 bug) | Critical | CI secret-scan; frontends architecturally cannot hold privileged keys |
